# 增强功能 10Why 深度分析

> 聚焦本项目核心场景：腾讯云 API 本地联调

---

## 一、断点调试 (Breakpoint)

**场景**: 开发者写了一个 @script onRequest，但不确定转换逻辑是否正确，想看看 `ctx.backendRequest` 实际长什么样再决定是否放行。

**10Why**:

1. **为什么需要断点？** 因为 JS 脚本出问题时，只能看日志猜测中间状态，效率极低。
2. **为什么不直接 console.log？** 因为 console.log 只能打印预定义的值，想临时看一个新变量需要改代码→保存→等热加载→再触发请求，往返 30 秒起步。
3. **为什么不能等请求结束再看？** 因为 onResponse 在转发后端之后才执行，如果 onRequest 写错了 `backendURL` 或 `backendRequest`，请求已经发到错误的地方了。
4. **为什么不用 Debug Tab 的 Dry Run？** Dry Run 只能模拟脚本执行，不会真正发往后端。当你需要"发到后端但不执行 onResponse"时 Dry Run 做不到。
5. **为什么需要"逐条放行"而不是全局开关？** 因为有时代理流量很大（页面加载几十个请求），只想精确拦截某一条，其余照常放行。
6. **为什么前端开发需要这个？** 前端开发代理 CDN 资源时，看似跟脚本无关。但当他们看到某个资源返回 404，想临时把代理目标从 `127.0.0.1:8322` 改成 `127.0.0.1:3000` 试一下——断点模式可以直接改 target 然后放行，不用改 rules 文件。
7. **为什么不是"修改规则文件再热加载"就够了？** 热加载有 2 秒延迟，而且改了规则忘了改回来会污染 git 记录。断点是临时的，不影响文件。
8. **为什么这是 P0 而非 P1？** 因为当前 yunapi-proxy 的调试手段只有 console.log + 手动 curl，竞争对手 Whistle 和 mitmproxy 都标配断点。这是体验的硬差距。
9. **为什么不直接用 Whistle？** 因为 Whistle 不支持 @script 嵌入式 JS，我们的脚本逻辑无法直接迁移。
10. **10 次调试有几次需要断点？** 估算：脚本开发阶段约 70% 的调试场景需要断点查看中间状态，比纯日志效率高 3-5 倍。

**判定**: ✅ 强烈建议。是本项目当前最大痛点。

## 二、域名树状分组 (Tree View)

**场景**: 页面加载后 Requests 列表瞬间涌入 80+ 请求，CDN 资源、API 调用、监控埋点混在一起，找一条特定 API 请求要翻好几页。

**10Why**:

1. **为什么需要分组？** 因为一个页面加载几十上百个请求，平铺列表无法快速定位目标。
2. **为什么不用过滤器？** 过滤器需要你**先知道** URL 长什么样，但树状分组只需要你认识域名或 path 结构，即可逐层展开找到目标。
3. **为什么域名分组就够了？** 云控制台场景下，不同域名代表不同业务：`cloudcache`=CDN、`console`=页面、`capi`=API。按域名分组天然对应业务边界。
4. **为什么需要二级展开？** 因为 `console.cloud.tencent.com` 下有几十个 `/cgi/capi` 和几十个静态资源，展开到这一级能看到 API 调用量和资源请求量的比例。
5. **为什么展示统计数字？** 树状节点旁显示 `(N)` 请求数和 `XXms avg`，一眼看出哪个 path 最慢，不用逐条点开看。
6. **为什么 whistle 的这个功能被高频使用？** 因为 whistle 的用户一样面对海量请求。它的实现是"折叠相同 URL"+统计，这是最高频的导航方式。
7. **为什么不用浏览器 DevTools Network 面板？** DevTools 只能看浏览器自身的请求，代理层面能看到全设备流量（手机、CLI 工具等）。
8. **为什么现在不实现以后也可以？** 可以，但每多一次迭代用户就多忍受一次平铺滚动。这是典型的"低成本高感知"改进。
9. **为什么成本低？** 只需前端改动：按 URL 提取域名 → 前端分组折叠 → 每行加缩进。后端零改动。
10. **为什么是 P1 而非 P0？** 因为可以用 URL 搜索临时撑住，不阻塞核心工作流。

**判定**: ✅ 建议。低投入(0.5d)，高感知。

## 三、性能瀑布图 (Timeline)

**场景**: 一个 API 调用耗时 3 秒，想知道时间花在了 JS 脚本上还是后端转发上。

**10Why**:

1. **为什么需要耗时分解？** 当前 `latency_ms` 只显示总耗时，无法区分脚本执行 vs 网络 I/O。
2. **为什么不直接用 Chrome DevTools？** DevTools 只能看浏览器的网络层，看不到代理侧的脚本执行时间。而且代理转发的是后端 HTTP 调用，不在浏览器视野内。
3. **为什么分解这几个阶段就够了？** 对于 yunapi 代理场景，最有价值的分解是：**onRequest 脚本耗时** + **后端 HTTP 转发耗时** + **onResponse 脚本耗时**。这三个已经覆盖了全部时间去向。
4. **为什么不是 DNS/TCP/TLS 这种经典瀑布图？** 因为本代理是反向代理模式——请求到代理的 TCP 层由浏览器完成，代理转发到后端是 HTTP 调用（通常已有长连接）。DNS/TCP/TLS 在代理→后端方向不显著。
5. **为什么 collect 时间数据？** `processorDispatcher.Process()` 里已经有 `time.Since(start)`，只是没分别在 onRequest/forward/onResponse 阶段打点。
6. **为什么不做成 whistle 那种复杂瀑布图？** 不必要。本项目的优势在于精准，不需要完整的水管分析。
7. **为什么后端改造小？** dispatch.go 的 processScript 里已经有天然的阶段边界：
   ```
   onRequest start → onRequest end
   forward start   → forward end  
   onResponse start→ onResponse end
   ```
   每个阶段 `time.Since()` 存入 Event 即可。
8. **为什么不是 P0？** 因为用户可以通过"对比两次相邻请求的耗时变化"反推优化效果，延迟分析不是阻塞性问题。
9. **为什么不是 P2？** 因为它确实能帮助定位性能瓶颈，而且实现简单，不应该排到最低优先级。
10. **为什么用户会感知到价值？** 当你把一个 API 的响应从 3 秒优化到 300ms 时，能清楚看到是"后端转发从 2.8s→0.1s"还是"脚本从 0.2s→0.2s"，这就是量化证据。

**判定**: ✅ 建议。投入低(1d)，后断点之后第二优先级。

## 四、请求对比 Diff

**场景**: 修改了 @script onResponse 的组装逻辑，想确认对同一个 API 的新旧响应有什么变化。

**10Why**:

1. **为什么需要对比？** 因为 yunapi 响应通常是几百行 JSON，肉眼对比极易漏掉深层差异。
2. **为什么不导出到 Beyond Compare？** 可以，但需要先手动复制两次响应 → 粘贴到文件 → 打开对比工具。UI 内一键对比省 5 个步骤。
3. **为什么不是浏览器控制台就能比？** 浏览器只能看到最终到达前端的响应（已通过 onResponse 处理），看不到处理前的原始响应。但我们想比的是"脚本改前 vs 改后的输出"。
4. **为什么不是每次都需要？** 对。只在修改脚本后验证时用，频率不高。
5. **为什么实现简单？** 纯前端：存上一次同 URL 的响应到 localStorage → 新响应来了 → JSON Diff 库对比 → 显示差异。后端零改动。
6. **为什么是同 URL 对比而非任意对比？** 因为最常用的场景就是"改了个字段，看结果变了没"。
7. **为什么不做成实时对比？** 不需要。主动触发即可。
8. **为什么是 json-diff 而非文本 diff？** 因为 JSON 语义比较比逐行文本 diff 更有意义——比如 key 顺序变了但语义相同，JSON diff 不会标出来。
9. **为什么 Reqable/Charles 都有这个功能？** 因为这也是他们的高频场景——改规则后验证输出变化。
10. **为什么排在瀑布图之后？** 使用频率低，且能用外部工具临时代替。

**判定**: 🟡 建议，P2 优先级。

## 五、HAR 导出

**场景**: 排查了一个小时的接口问题，想把自己看到的请求上下文分享给后端同事。

**10Why**:

1. **为什么需要导出？** 因为后端同事不一定在本地装代理，但 HAR 是通用格式，Chrome DevTools 直接能打开。
2. **为什么不截图？** 截图只能看几行 URL，丢失了 headers、body、耗时等关键信息。
3. **为什么是 HAR 而非 CSV？** HAR 是 W3C 标准，包含完整的请求/响应/耗时/时间线，Chrome DevTools Network 面板原生支持导入。
4. **为什么不直接在 UI 里做分享链接？** 因为代理在本地 localhost，外网不可达。导出文件是唯一可行的跨机器分享方式。
5. **为什么频率低但价值高？** 平时用不上，但一旦需要协作 debug，HAR 文件比自己口头描述"状态码是 500，body 大概是..."高效 10 倍。
6. **为什么后端实现简单？** `GET /api/requests?format=har` → 遍历广播器缓冲区 → 组装 HAR JSON。30 分钟。
7. **为什么不做到 Q3？** 因为当前团队规模小，协作需求不迫切。
8. **为什么不是 P3？** 因为 HAR 导出的实现成本极低，做一个放在那里就有价值。
9. **为什么 whistle 和 mitmproxy 都支持？** 因为这是调试代理工具的事实标准——就像 PSD 于设计工具。
10. **为什么不做就在产品完整性上扣分？** 用户分享请求时说"我用 yunapi-proxy 抓到了，但没法导出你看"，工具的传播力就打折扣了。

**判定**: 🟡 建议，P2 优先级，但投入低(0.5d)。

## 六、最终排序

| 优先级 | 功能 | 投入 | 用户价值 | 10Why 结论 |
|:--:|------|:--:|:--:|------|
| **P0** | 断点调试 | 2d | 🔴 极高 | 核心调试手段缺失，竞品标配 |
| **P1** | 域名树状分组 | 0.5d | 🟡 高 | 低成本高感知，每次打开都受益 |
| **P1** | 性能阶段分解 | 1d | 🟡 高 | 量化性能优化，后端改动小 |
| **P2** | 请求对比 Diff | 0.5d | 🟢 中 | 低频但关键时刻有用 |
| **P2** | HAR 导出 | 0.5d | 🟢 中 | 行业标准，低成本补齐 |

**可砍掉**: Mock（用户不需要）、远程设备代理（场景不匹配）、WebSocket 帧查看（yunapi 无此协议）、gRPC（同上）
