# 实用性 10Why — 聚焦日常调试工作流

> 不以"竞品有没有"为标准，以"今天早上改个 script 用了多久"为标准。

---

## 先还原一次真实的调试经历

```
09:30  浏览器报错 "region invalid"
09:31  打开 yunapi Web UI → Requests tab
09:31  在 60+ 条请求中翻找 console.cloud.tencent.com 的 API 调用
09:32  找到了，点开看 reqBody: {regionId: 1}，respBody: {code: 500}
09:33  切换到 Rules tab → 点 apm-dev → 看 onRequest 脚本
09:34  发现：cfg.region_map[String(body.regionId)] 这里的 key 是数字不是字符串
09:35  改成 cfg.region_map[Number(body.regionId)]
09:35  Ctrl+S 保存
09:35  等热加载生效（2 秒）
09:36  切回浏览器 → 刷新页面 → 重新触发请求
09:36  切回 Requests tab → 翻找新的 API 请求
09:37  找到了，点开看 respBody → 还是 500
09:38  发现 Number() 改对了，但 region_map 里是字符串 "1" 不是数字 1
09:39  又改回 String()
09:39  Ctrl+S
09:40  刷新浏览器 → 翻找请求 → 还是 500
09:41  ...（10 分钟后发现是另一个字段的问题）
```

**这个循环里，真正在"写代码"的时间：2 分钟。真正在"找请求、等刷新"的时间：8 分钟。**

---

## 用 10Why 解剖这个流程

### Q1: 为什么翻找请求要花 2 分钟？

**因为** 60 条请求平铺在一起，CDN 的 `cloudcache`、API 的 `console/cgi/capi`、埋点的 `otheve` 全混着。你脑子里想的是"那个 POST 请求"，但眼睛看到的是 60 行几乎一样的 URL。

→ 如果按域名分组：`cloudcache` 折叠 40 个 CDN 请求，一下就定位到 `console` 下的 3 个 API 调用。

### Q2: 为什么改一行代码要等 15 秒才能验证？

**因为** 流程是：Ctrl+S → 热加载 2s → 切浏览器 → F5 → 等页面加载 → 切回 UI → 找到新请求。这是 6 个步骤，每一步都有心理负担。

→ 如果 UI 里有 "Resend 按钮" —— 但我们已经有了！问题是：Resend 会走代理管线，触发了新的 script 执行。这个其实已经是优化后的版本了。

### Q3: 什么还能再加速这个验证循环？

**不是加速单个步骤，而是减少"写错了→验证→再写→再验证"的迭代次数。**

你要的是**写一次就写对**。实现方式是：在保存前就能预览脚本的输出。

→ Debug Tab 的 Dry Run 已经部分做到了。但它只跑脚本，不真正转发后端。**如果 Debug Tab 能"Dry Run + 后端转发 + 返回完整响应"**，那就能在保存前看到完整效果。

### Q4: 那断点调试的价值是什么？

断点调试解决的是另一个问题：**"我已经发了真实请求，但不知道中间态出了什么错"**。

- 断点模式下，一个匹配的请求到达代理时，UI 自动弹出"已拦截"通知
- 点击展开，你能看到 `ctx.backendRequest` 的实际 JSON 对象
- 你可以**即时修改** `backendURL` 或 `backendRequest` 的任何字段，然后点"继续"
- 转发到后端，响应回来后，再看到 `ctx.backendResp`
- 可以再**即时修改** `finalResp`，然后点"继续"
- 最终响应发给浏览器

**这让"改规则→等热加载→刷新→等请求→看结果"的 15 秒循环，变成"拦截→看一眼→继续"的 3 秒操作。**

### Q5: 但是，断点调试真的是最急需的吗？

用一个问题判断：

> **你上次改脚本，改了 3 次以上才改对，而不是一次性改对的——这种经历最近一周有几次？**

如果每周都有 3+ 次，那断点调试就是 ROI 最高的功能。

如果你大多数时候能一次改对，那你的痛点就不是"试错成本"，而是"找到正确请求并理解数据的成本"。

### Q6: 那如果痛点更多是"找到请求"，具体要解决什么？

三个问题交织：
1. **定位请求慢**（平铺列表翻页）
2. **理解数据慢**（同 URL 多次请求，不知道哪个是改完后的）
3. **对比改前改后慢**（眼睛来回看两行）

→ **树状分组 + 时间排序 + 当前过滤** 已经解决了 80% 的"定位"问题（0.5d 前端改动就够了）

→ **自动高亮最近一次同 URL 请求** 可以解决"理解数据"问题：你改完 script 后 refresh 浏览器，新请求到达时自动高亮那条最新的 `console.cloud.tencent.com/cgi/capi?action=delegate`

→ **请求 Diff** 可以在你点开一条请求时，如果历史里存在同 URL 的上一条，自动在响应区域旁显示"跟上次有什么变化"。

### Q7: 那这三个合起来，日常调试流程变成什么样？

```
09:30  浏览器报错
09:30  打开 Web UI → Requests tab
        树状分组已经折叠了 CDN 资源，一眼看到 console.cloud.tencent.com
        展开 → (3) 3 条 API 调用
09:31  点击最新那条（自动高亮的）
        详情面板 → Response tab
        旁边自动显示 [Diff from previous]，highlight 出变化：
        "regionId" 从 25 变成 23，"Region" 从 "ap-bangkok" 变成 "ap-bangkok"（没变？哦原来是 region_map 没生效）
09:32  切 Rules → 改脚本
09:33  在 Resend 面板编辑请求 → regionId 改成 23 → Send
09:33  新请求出现在列表，自动高亮
        点开看 Response → [Diff] 显示 Region 正确了
```

**从发现到定位到验证完成：3 分钟。刚才那个流程是 10 分钟。**

### Q8: 这三个功能里哪个最难实现？

| 功能 | 前端 | 后端 | 复杂度 |
|------|:--:|:--:|:--:|
| 树状分组 | ✅ | ❌ | 纯前端 CSS + JS |
| 自动高亮最新同 URL | ✅ | ❌ | 前端逻辑 |
| 请求 Diff | ✅ | ❌ | JSON diff 库 |

**都是纯前端改，0 后端改动。**

### Q9: 那断点调试呢，还做不做？

做，但应该分两步：

**Step 1（0.5d）**: 先做"**即时脚本测试**"模式——
- 在 Resend 面板里，用实际后端转发代替 Dry Run
- 你改完请求参数 → Send → 看到完整响应（走真实后端+脚本）
- 效果：不用切浏览器刷新，在 UI 里就能完成"改参数→发请求→看结果"

这个我们**其实已经做了**（Resend 走代理管线）！

**Step 2（2d）**: 再做真正的断点拦截——
- 匹配的请求到达时自动暂停
- 可以修改中间变量
- 继续执行

### Q10: 所以，最终结论是什么？

**断点调试不是"下一个该做的功能"，树状分组+Diff+自动高亮才是。**

为什么？

> **因为 yunapi-proxy 的用户每天 80% 的时间花在"找到请求、理解数据"上，只有 20% 在"调试脚本逻辑"上。先消灭 80%，再优化 20%。**

断点调试虽然炫，但解决的是你已经找到了目标请求之后的"脚本级调试"。而你现在连找到目标请求都还在平铺翻页。
