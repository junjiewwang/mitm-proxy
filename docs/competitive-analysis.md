## 三、yunapi-proxy 优势与差距

### 🟢 核心优势 (差异化竞争力)
| 优势 | 说明 |
|------|------|
| **嵌入式 JS 脚本** | 规则文件内嵌 `@script`，配置和逻辑内聚。Whistle 需要装 plugin，mitmproxy 需要额外 Python 文件 |
| **Go 原生高性能** | 极低内存占用，高并发优势明显 |
| **YAML 私有配置** | `@config` 透传业务配置到 JS，其他工具无此模式 |
| **热加载** | 修改规则文件即时生效，无需重启 |
| **浏览器级 Web UI** | 无安装，跨平台零成本 |

### 🔴 功能缺口 (按影响排序)
| 等级 | 功能 | yunapi-proxy 现状 | Whistle/mitmproxy |
|------|------|-------------------|-------------------|
| **P0** | 断点调试 (Breakpoint) | ❌ 只能在脚本中写逻辑 | 可实时拦截逐条放行/修改 |
| **P0** | Mock/Stub | ⚠️ 需写 JS onRequest 返回 | whistle values 可视配置 |
| **P1** | 性能瀑布图 | ❌ | 各工具均有 DNS/TCP/TLS 分析 |
| **P1** | WebSocket 调试 | ❌ | 全产品支持 |
| **P1** | 树状域名分组 | ❌ | 大量请求时导航必备 |
| **P2** | HAR 导出 | ❌ | 行业标准，便于分享 |
| **P2** | 请求对比 (Diff) | ❌ | Reqable/Charles 支持同URL两次响应对比 |
| **P2** | 流量录制回放 | ❌ | 可录制一组请求序列回放 |
| **P3** | 远程设备代理 | ❌ | 手机APP调试刚需 |
| **P3** | CLI 工具 | ❌ | w2/mitmdump 持续集成场景 |

## 四、10Why 分析

### Why 1: 为什么需要这个代理工具？
因为腾讯云 API 调试需要本地环境直接对接控制台前端，而线上 yunapi 网关对请求格式有特殊要求（三层嵌套），本地无法直连。

### Why 2: 为什么需要 JS 脚本化？
因为不同 API（APM、计费、CDN）的请求/响应转换逻辑各不相同，且经常随业务变更。硬编码在 Go 里维护成本高，用 JS 脚本业务方可以自行修改。

### Why 3: 为什么需要 Web UI？
因为命令行看日志效率低，团队成员需要可视化观察请求流量、快速定位问题。Web UI 零安装，任何浏览器都能用。

### Why 4: 为什么需要热加载？
因为开发过程中频繁调整规则脚本，如果每次都要重启代理，会打断调试流程。热加载 2 秒内生效，保证开发效率。

### Why 5: 为什么需要请求重放 (Replay)？
因为在排查 API 问题时常需要反复发送同一请求验证修复效果。手动 curl 需要重新构造完整的认证头和签名，浪费时间。

### Why 6: 为什么需要编辑重发 (Edit & Resend)？
因为修改请求参数（如 regionId、action 命令）后重新发送是高频操作。只有 replay（原样重发）不够，需要能编辑。

### Why 7: 为什么需要断点调试？
因为脚本流程复杂（onRequest → 转发 → onResponse），错误常出在中间环节。没有断点只能打印日志猜测，效率极低。

### Why 8: 为什么需要 Mock/Stub？
因为调试前端 UI 时需要模拟后端各种返回（正常/异常/边缘），而真实后端不一定随时能产生这些场景。Mock 可以快速切换场景。

### Why 9: 为什么需要 HAR 导出/团队协作？
因为排查复杂 bug 时需要跨团队（前端、后端、运维）协同。把请求上下文导出为 HAR 文件，任何人都能在 Chrome DevTools 中打开分析。

### Why 10: 为什么需要关注竞品？
因为代理工具市场竞争激烈，Whistle 有 15k+ star、Reqable 增长迅猛。不持续演进，用户会流向体验更好的产品。**核心壁垒是"腾讯云 API 专用+JS 脚本一体化"这个差异化定位**。

## 五、5W1H 分析

### What (做什么)
做一个面向腾讯云 API 调试的**可编程代理平台**，同时满足以下角色：
- **前端开发**: 本地资源代理，Web UI 可视化
- **后端开发**: HTTPS 抓包，请求重放
- **规则开发者**: JS 脚本热插拔，编译检查
- **团队协作**: 规则共享，HAR 导出

### Who (给谁用)
| 用户 | 场景 | 频率 |
|------|------|------|
| 前端开发 | CDN 资源代理到本地 dev-server | 每日 |
| 后端开发 | API 响应查看、请求重放验证 | 每日 |
| 规则开发者 | 编写 @script 转换逻辑 | 每周 |
| QA 测试 | Mock 数据验证 UI 行为 | 按需 |

### When (何时用)
- **开发阶段**: 前端后台联调，本地代理
- **调试阶段**: 排查 API 参数/响应问题
- **验证阶段**: 重放请求确认修复
- **回归阶段**: 修改规则脚本后验证

### Where (在哪里用)
- 开发者本地机器 (macOS/Windows/Linux)
- CI/CD 环境（通过 CLI 工具，后续）
- 团队共享环境（规则文件 git 管理）

### Why (为什么选它)
**首选理由**: 与腾讯云 API 原生集成——yunapi 三层嵌套格式是定制需求，通用代理工具（Whistle/Charles）需要大量配置才能适配。yunapi-proxy 的 @script 模式开箱即用。

**替代理由**: 如果只需要通用 HTTP 抓包，Whistle 社区生态更成熟；如果需要移动端抓包，Reqable 体验更好。

### How (怎么做——路线图)

```
Q3 2026 (当前季度)
├── P0: 断点调试 — 单步放行/修改/丢弃请求
├── P0: Mock 规则 — 可视化配置 mock 响应，无需写 JS
├── P1: 性能瀑布图 — 请求耗时分解 (DNS/TCP/TLS/Req/Resp)
└── P1: 树状分组 — 按域名/路径折叠请求列表

Q4 2026
├── P2: HAR 导出 — Session → HAR 文件
├── P2: 请求对比 — 同 URL 两次响应 Diff
├── P1: WebSocket 帧查看
└── P3: CLI 工具 — mitmctl 命令行模式

2027
├── P3: 远程设备代理 — 手机扫码连接
├── 流量录制回放
└── 团队协作空间
```
